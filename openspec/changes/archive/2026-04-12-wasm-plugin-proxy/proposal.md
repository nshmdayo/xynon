## Why

ユーザーは Go 言語で拡張可能なプロキシサーバを構築したい。ホストは標準ライブラリ中心のシンプルな Go 実装に保ちつつ、リクエスト/レスポンス処理を WASM プラグインで拡張できる仕組みを求めている。加えて、プロキシを再起動せずにプラグインを差し替えられるホットリロード機能が必要で、これがないと運用中のポリシー変更やプラグイン開発のイテレーションが遅くなる。

## What Changes

- 標準 `net/http` / `net/http/httputil` をベースにした HTTP フォワードプロキシホストを新規追加する。
- WASM プラグインをロード・実行するためのプラグインランタイムレイヤを追加する（ホスト ABI、呼び出しフック、サンドボックス境界を含む）。
- プラグインファイルの変更を監視して無停止でリロードするホットリロード機構を追加する。
- プラグインがフックできるリクエストライフサイクル上の拡張ポイントを定義する（例: `on_request`, `on_response`）。
- プラグインディレクトリやフィルタリング順序などを設定するための設定ファイル形式を定義する。
- 最小構成で動作させるためのサンプルプラグイン（ヘッダ書き換えなど）とローカル実行用の CLI エントリポイントを追加する。

## Capabilities

### New Capabilities
- `proxy-host`: 標準 Go で実装された HTTP フォワードプロキシ本体。リスナ、リクエスト転送、プラグインチェーンへのディスパッチを担当する。
- `wasm-plugin-runtime`: WASM モジュールのロード、インスタンス化、ホスト ABI、リクエスト/レスポンスフックの実行を担当するランタイムレイヤ。
- `plugin-hot-reload`: プラグインファイルを監視し、実行中のプロキシにダウンタイムなくプラグインを反映させる仕組み。
- `proxy-config`: プロキシ動作とプラグインセットを宣言するための設定ファイルフォーマットとローダ。

## Impact

- 新規 Go モジュール（`go.mod`）とディレクトリ構成（`cmd/`, `internal/proxy`, `internal/plugin`, `internal/config` 等）を作成する。
- WASM ランタイムライブラリ（wazero など純 Go 実装）への依存が追加される。ホスト側のビルドは CGO 不要のまま保つ。
- プラグインは WASM バイナリとして別途ビルドする必要があり、サンプル用のビルドパイプラインが追加される。
- 運用面ではプラグインディレクトリのパーミッションや信頼境界の考え方が新しい論点として発生する。
- 既存コードベースは空に近い状態のため、破壊的変更は発生しない。
