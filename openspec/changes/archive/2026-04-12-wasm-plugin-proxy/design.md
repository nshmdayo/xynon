## Context

このリポジトリ（Xynon）は現状ほぼ空で、Go 言語で拡張可能なプロキシアプリを新規に構築するフェーズにある。ユーザーの要求は大きく 3 点あり、(1) ホストとなるプロキシは「標準の Go」で書きたい、(2) リクエスト/レスポンスの加工ロジックは WASM プラグインとして差し込める、(3) プラグインはホットリロードで入れ替えられる、というものである。

ホストが標準 Go 中心であることには 2 つの含意がある。第一に、`net/http` と `net/http/httputil.ReverseProxy` を基盤として使うことで、HTTP セマンティクス（ホップバイホップヘッダの扱い、Host 書き換え、接続プール、HTTPS トンネリング等）の自前実装を避ける。第二に、ホストのビルド・配布を CGO なしで完結させたい。この結果、WASM ランタイムも純 Go 実装である必要がある。

プラグインは WASM として提供されるため、言語非依存かつサンドボックス境界が明確で、任意のユーザーコードを同一プロセス内で実行してもホストを直接破壊できないことが期待できる。一方で、WASM はメモリ境界を越えるデータ受け渡しに注意が必要で、プラグインとホストの間で流れるデータ（リクエストヘッダ、ボディ、メタ情報）について明示的な ABI を設計する必要がある。

ステークホルダーは主にプロキシ運用者とプラグイン開発者の 2 種類である。前者はホットリロード時のゼロダウンタイムと安全性、後者は ABI の安定性と開発体験（例: サンプルプラグインがすぐに動くこと）を重視する。

## Goals / Non-Goals

**Goals:**
- 標準 `net/http` / `httputil.ReverseProxy` ベースの HTTP フォワードプロキシホストを提供する。
- WASM モジュールを実行できるプラグインランタイムを提供し、リクエスト・レスポンス両方のフック実行を可能にする。
- プラグインディレクトリを監視し、ファイル追加・更新・削除を検知して実行中のホストに反映するホットリロードを提供する。
- ホスト・プラグイン間の ABI を明示的に定義し、ヘッダ参照・変更など最小限の操作を安定した API として提供する。
- 設定ファイル（YAML または TOML）で、リスンアドレス・プラグインディレクトリ・プラグインチェーン順序などを宣言できるようにする。
- ホストのビルドは CGO なし（`CGO_ENABLED=0` でビルド可能）に保つ。

**Non-Goals:**
- 本変更ではプロトコルを HTTP/1.1・HTTP/2（`net/http` が透過的にサポートする範囲）に限定する。HTTP/3、任意 TCP プロキシ、独自プロトコル対応は対象外。
- プラグイン配布システム（レジストリ、署名、バージョン解決）は対象外。ローカルファイルシステム上の WASM ファイルを前提とする。
- マルチテナント・権限分離・認証認可の高度な仕組みは対象外。まずは単一運用者前提の最小構成を作る。
- ホストレベルの TLS 終端や MITM（復号）機能は今回の範囲外。まずはプレーン HTTP での拡張ポイント検証を優先する。
- 本変更ではメトリクス・分散トレーシング基盤の導入までは行わない（ログ出力のみ）。

## Decisions

### Decision 1: WASM ランタイムは wazero（純 Go）を採用する

- **選択**: `github.com/tetratelabs/wazero` を WASM ランタイムとして使用する。
- **理由**: 純 Go 実装で CGO 不要、標準 Go ビルドに自然に組み込める。WASI プレビュー 1 もサポートされており、Go/Rust/TinyGo 等で書いたプラグインの動作実績が豊富である。API が stable で、モジュールのコンパイルキャッシュや複数インスタンス化など、ホットリロード用途で必要な機能が揃っている。
- **代替案と却下理由**:
  - *wasmtime-go*: 性能面では有力だが CGO 依存であり「標準 Go でビルドしたい」という要件に反する。
  - *自前インタープリタ*: 再発明コストに見合わない。

### Decision 2: ホストはプラグインを「チェーン」として呼び出す

- **選択**: 設定ファイルに宣言された順序で複数プラグインを直列に呼び出し、各プラグインが `on_request` / `on_response` フックを実装する。
- **理由**: `httputil.ReverseProxy` の `Director` と `ModifyResponse` に自然にマッピングでき、実装が単純。順序が明示的になり、運用者にとって挙動が予測しやすい。
- **代替案と却下理由**:
  - *イベントバス/pub-sub 型*: 柔軟だが順序と副作用が追いづらく、初期バージョンには過剰。

### Decision 3: ABI は「ハンドルベース + ゲスト関数」方式

- **選択**: ホストは各リクエスト/レスポンスに整数ハンドル ID を割り当て、ゲストは `get_header(handle, name)` / `set_header(handle, name, value)` のようなホスト関数を通じてのみアクセスする。プラグインは `on_request(handle) -> action` と `on_response(handle) -> action` をエクスポートする。
- **理由**: WASM ではゲスト側に大きな構造体を丸ごとコピーして渡すのは非効率かつ危険。ハンドル方式ならゼロコピーに近い形で必要な部分だけを参照・変更できる。`action` はプラグインの意思表示（続行/短絡応答/エラー）をホストに返すための enum 相当の整数。
- **代替案と却下理由**:
  - *Protobuf シリアライズ*: 表現力はあるが初期実装の複雑度が高く、ABI 境界を不安定にする。
  - *WIT/Component Model*: 将来の最有力候補だが、wazero の Component Model サポートの熟度と初期スコープを考慮し、今回は見送る。ABI 設計は将来 Component Model へ移行できる形（ハンドル + 名前付き関数）にしておく。

### Decision 4: ホットリロードは fsnotify ベース + 世代管理

- **選択**: `github.com/fsnotify/fsnotify` でプラグインディレクトリを監視し、変更を検知したらプラグインチェーンの「新しい世代（generation）」を構築する。構築完了後にアトミックにスワップし、旧世代は進行中のリクエストが終わり次第破棄する。
- **理由**: プロセス再起動なしでの差し替えが目的であり、リクエスト単位でプラグインチェーンのスナップショットを参照させれば、進行中リクエストは旧世代を使い、新規リクエストから新世代が適用される。これにより部分的に切り替わった不整合状態を避けられる。
- **代替案と却下理由**:
  - *SIGHUP で全リロード*: 実装は単純だが「無停止」という要件に対する体験がやや劣る。運用者が明示的に操作する必要があり、開発イテレーション速度も落ちる。ただし fsnotify と併用可能な補助手段として残してもよい。
  - *ファイル単位でインプレース差し替え*: 実装が繊細で、チェーン内の依存関係で中途半端な状態を作りやすい。チェーン全体を世代単位で扱う方が安全。

### Decision 5: チェーンスナップショットは `atomic.Pointer[Chain]` で共有する

- **選択**: 現在有効なチェーンを `atomic.Pointer[Chain]` に保持し、各リクエストは処理開始時に 1 度 `Load()` してローカル変数にコピーしたものを使う。ホットリロード時は新しい `*Chain` を `Store()` するだけ。
- **理由**: ロックフリーで読み取りが高速、実装がシンプル。リクエストがチェーンを処理し終わるまで旧世代は GC 対象にならない（参照が残るため）ので、途中で消える心配がない。
- **代替案と却下理由**:
  - *sync.RWMutex*: 動くがリクエストパスに毎回ロックを入れる必要があり、不要なオーバーヘッドが出る。

### Decision 6: 設定ファイルは YAML、ロードは起動時のみ

- **選択**: 設定ファイルは YAML、起動時に 1 度読み込む。ホットリロード対象は「プラグインディレクトリ内の WASM ファイル」に限定し、設定ファイル自体の変更は再起動を要求する。
- **理由**: スコープを絞ることで初期実装を単純化する。設定ファイルの動的リロードは需要が出てから別変更として扱う。

## Risks / Trade-offs

- **[リスク] WASM プラグインがボディ全体を読まないと動けないケースで、ストリーミング転送ができずメモリ使用量が跳ね上がる** → 初期バージョンではプラグインがボディを要求した場合のみ全量バッファし、そうでなければストリーミングのままパススルーする。ABI に `needs_body` のような宣言を入れて、不要なバッファリングを避ける。
- **[リスク] プラグインが無限ループ・大量メモリ確保でホストを巻き込む** → wazero のコンテキストキャンセルと実行時間ガードを使い、1 フックあたりの実行時間と最大メモリを設定で制限する。違反時はそのプラグインをチェーンから除外し、エラーログに残す。
- **[リスク] ホットリロード中にプラグインファイルが部分書き込み状態で検知されて読み込み失敗する** → fsnotify で検知後に短いデバウンス（例: 200ms）を入れ、`os.Stat` でサイズが安定したことを確認してからロードする。ロード失敗時は旧世代を維持して警告ログを出す（失敗しても現行動作は落ちない）。
- **[リスク] ABI の早期確定がユーザーコードと結合し、将来の Component Model 移行を阻害する** → ABI をホスト側 1 箇所（`internal/plugin/abi`）に閉じ込め、バージョン番号を付与しておく。プラグインはエクスポート関数で ABI バージョンを申告し、不一致時はロードを拒否する。
- **[リスク] プラグインディレクトリがネットワーク越し（NFS 等）に置かれると fsnotify が機能しない環境がある** → ドキュメントでローカルファイルシステム前提であることを明示し、必要に応じてポーリングフォールバックを将来追加する余地を残す。
- **[トレードオフ] HTTPS を透過的に扱わない** → MITM を今回のスコープから外すことで、設計・実装が大幅に単純化される。代わりに HTTPS リクエストは CONNECT トンネリングのみサポートし、プラグインからは中身が見えないことを明示する。

## Migration Plan

既存コードがほぼ存在しないため、マイグレーションは主に新規構築である。

1. 新規モジュール初期化（`go mod init`）と最小ホスト骨格の追加。
2. wazero と fsnotify の依存追加、プラグインランタイムと ABI の最小実装。
3. ホットリロードの世代切り替えを追加し、サンプルプラグインで動作確認。
4. 設定ファイルローダとサンプル設定・サンプルプラグインのビルド手順を追加。
5. README 等のドキュメント化は本変更のスコープ内では最小限（起動コマンドと設定例のみ）に留める。

ロールバック戦略: 本変更はゼロからの追加であり、問題があればコミット単位で巻き戻せる。運用ロールバックとしては、ホットリロード機能に不具合が見つかった場合に限り、プラグインチェーンを起動時固定（リロード無効）で動かすフラグを用意しておくと安全。
